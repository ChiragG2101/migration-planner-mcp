# Invariants

Numbered rules that must always hold. Each names the test that fails when the rule breaks. Numbers are never reused: a removed rule is marked `retired` with the reason, not deleted.

**Planned and live.** A *planned* test path comes from the milestone plans and doesn't exist yet. The milestone that adds each guard also adds its test and flips the invariant to *live*, naming the real tests. An invariant without a passing test is not satisfied; it is a promise the milestone must keep. M1's invariants are live (INV-1 to INV-6 for M1's part, INV-12 to INV-14, INV-46, INV-47); M2 adds INV-48 to INV-50 and its parts of INV-4, INV-13, INV-15 and INV-27. M3 adds INV-10, INV-24, INV-28, INV-32, INV-33, INV-36 to INV-39 and INV-51 to INV-53. M4 adds INV-11, INV-35, INV-54 and INV-55. M5 adds INV-56 and INV-57 and its parts of INV-4, INV-5, INV-13, INV-22, INV-23 and INV-42. M6 adds the gate code behind INV-15 to INV-20 and INV-29, the aggregator part of INV-42, and INV-58 to INV-60. M7 makes INV-25, INV-30, INV-31, INV-43, INV-44 and INV-45 live (the eval runner, replay, the pack gate and the add-only check) and completes the finder part of INV-41; its golden-case data (real cases with recorded runs and a published noise band) lands in a later live session, so M7's live tests run on in-code fixture cases and recorded runs built inside `test/unit/eval/`, and the committed `eval/results.md` reports no recorded golden runs yet (D39). ## Out of scope (see `design.md` D16)

- **INV-42:** Every `out_of_scope` entry has a non-empty reason and a `written_by` (`scope`, `engine` or a lens). A lens can only mark usage IDs from its own packet, a usage keeps one entry (`scope`, then `engine`, then a lens), and every usage that matches no composed rule and that no finding covers gets the engine's `no rule in range` reason, in every run size. A usage covered by a finding never also gets the engine's reason or a lens entry; a lens mark on it is recorded as a conflict event. Scope-excluded usages are in no lens packet, and one that a finding still covers keeps its `scope` entry: the usage is removed from the finding's coverage and recorded as a conflict event, and the finding stays in the plan for its other usages. A finding left covering no usage is kept out of the plan and listed in the run report. A submission in which one lens both marks a usage out of scope and writes a finding on it is rejected whole, with no item stored, and counts toward the lens retry policy. *(live: `test/unit/submitFindings.test.ts`, `test/unit/packets.test.ts` — M5; the aggregator part `src/pipeline/aggregate.ts`, `test/unit/aggregate.test.ts`, and gate 2 `test/unit/gates/gates.test.ts` — M6)*

## Pack merge gate (see `design.md` D17)

- **INV-43:** On every PR, CI replays the recorded runs (engine runs through HEAD's engine, baseline runs re-scored from their recorded Markdown). Recall is golden-set usage recall pooled over a pack's cases; the engine's figure is its worst-case pooled recall (each case's lowest-recall run) and the baseline's is its best-case pooled recall (each case's highest-recall run), so renumbering runs never changes either. For each pack under `packs/` at HEAD, the PR fails if: the pack has no band in `eval/results.md` on the base branch and the engine's figure is not above the baseline's (`nextjs-upgrade`, which sets the first band in M7, is exempt); the PR adds golden cases to a pack other than `nextjs-upgrade` and, over all its cases, the engine's figure is not above the baseline's (for `nextjs-upgrade` this is shown, not enforced); the engine's figure over the cases in the base band that are present at HEAD falls below the low end of the base band over the same cases (skipped, and said so in the CI job output, when the base branch has no band for the pack); the pack has fewer than 2 golden cases or no true changed usage; any case has fewer than 3 runs on either side, or run counts differ across the pack's cases or between the engine and the baseline; the pack's runs, on both sides, don't all share one host product and model; or a pinned case commit can't be fetched and isn't cached (a named `case_commit_unavailable` error, never a skipped case). It also fails if the committed `eval/results.md` differs from the re-scored one. `results.md` is a pure function of HEAD's tree: it holds no generation time, takes cost and wall time from the recorded runs, records the engine by its package version, always reports each pack's all-case beat result, and renders `eval/cases/REMOVED.json`; verdicts that depend on the base branch (regression pass or fail, a skipped regression check, a reported widening beat result) go only in the CI job output. *(live: `eval/packGate.ts` with the `eval:pack-gate` CI step in `.github/workflows/ci.yml`, `eval/results.ts`, `test/unit/eval/packGate.test.ts` and `test/unit/eval/results.test.ts` on in-code recorded-run fixtures — M7; applied to the Django pack — M10)*
- **INV-44:** The pack gate and `eval/results.md` score only engine runs under the current prompt version that `prompts/manifest.json` names at HEAD, and only baseline runs whose recorded hash of `eval/baseline/prompt.md` equals HEAD's; a pack with a baseline run of another hash fails. Cases whose pack doesn't exist under `packs/` at HEAD are listed as pending in `results.md`, never scored or failed. Every engine run records its ingest arguments, `set_scope` answers, every `run_docs` entry whatever its `fetched_by` (URL, content, `doc_id`, `fetched_by`, `official`, status), each `validate_plan` round's lens submissions in order, and the file, span and `snippet_hash` of every usage ID its packets carried; `truth.json` stores the same three per true usage. Replay never calls a model or Context7 and adds no agent turns: it applies the recorded arguments and scope answers, re-registers every recorded doc with no network, and feeds the rounds in order, stopping at the first round HEAD's gates pass, through HEAD's `find_usages`, packets, `merge_findings` and gates, keeping each run's recorded size and lens set (a run HEAD would size differently is flagged in the report, never re-sized). Later recorded rounds are not fed. A recorded input HEAD rejects is handled as the live flow would and the run is flagged: a scope answer HEAD no longer offers takes the default, a submission HEAD's `submit_findings` rejects counts as that lens's invalid output (using the recorded retry attempts, then `lens.gap`), and a doc HEAD's version pin refuses is not registered. A failure HEAD's gates newly raise, with no recorded round left, goes to `unresolved` and is scored, never patched. Recorded usage IDs and truth usages are matched to HEAD's usages by file, span and `snippet_hash`, never by usage ID, so renumbering IDs leaves the score unchanged; a recorded finding with no matching HEAD usage is dropped, counted as a miss and listed, and `truth.json` is never re-derived for an existing case. A change to usage spans or the snippet normaliser therefore fails the regression check on the affected cases unless, in the same core PR, they are removed under exception (b) and re-added under new IDs with fresh truth and new runs; the re-added cases are new cases of their pack, outside the regression check's base cases and inside the all-case beat check. *(live: `eval/replay.ts` and `eval/packGate.ts`, with replay driving HEAD's `proposeScope`/`setScope`/`getMigrationDocs`/`getLensPacket`/`submitFindings`/`mergeFindings`/`validatePlan` and Context7 disabled through the shared `REPLAY_DOCS` (`apiKey: null`) in `eval/engineRun.ts`, `test/unit/eval/replay.test.ts` (the "registers recorded docs with no network" fixture re-registers a cited doc through a throwing `fetch` and passes gate 3, and the guard case proves flipping `REPLAY_DOCS` off `null` reaches the network) and `test/unit/eval/packGate.test.ts` — M7)*

## Eval data (see `design.md` D15)

- **INV-45:** On every PR, existing cases (case folders with recorded runs on the base branch) and recorded runs are add-only: no file in an existing case's folder is added, changed or deleted, the folder is not deleted, no existing run is changed or deleted, and no run is added to a set that already has runs on the base branch. A set is a case's engine runs under one prompt version, its L1 set under that version (`eval/runs/<case>/<prompt_version>/l1/<n>/`, which never counts toward N or recall) or its baseline runs; runs under a new prompt version, and a case's first L1 set under a version, are plain adding. The one allowance is `annotations.json`, which may gain appended entries (or be added with its first entries) while its existing entries stay frozen. Deleting a single run without removing its case always fails. A pending case (no recorded runs) is removed only through (b), never by a pack PR. The only exceptions are (a) a core PR that changes `eval/baseline/prompt.md`, which may replace baseline runs and nothing else (no engine run, no case file), and (b) removing a case with all its runs in a core PR (one that changes nothing under `packs/` or `knowledge/`) that adds an entry to the add-only `eval/cases/REMOVED.json`; an entry with no matching case removal fails, and existing entries are never edited or deleted. Exception (b) is also how a change to usage spans or the snippet normaliser re-adds its affected cases under new IDs. Its maintainer review is enforced by GitHub's required code-owner review through `.github/CODEOWNERS`, not by CI (`design.md` D15). *(live: `eval/addOnly.ts` and `scripts/check-eval-add-only.ts` with the `eval:add-only` CI step in `.github/workflows/ci.yml`, `.github/CODEOWNERS` naming the maintainer for `eval/cases/**` and `eval/runs/**`, `test/unit/eval/addOnly.test.ts` — M7)*
