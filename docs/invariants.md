# Invariants

Numbered rules that must always hold. Each names the test that fails when the rule breaks. Numbers are never reused: a removed rule is marked `retired` with the reason, not deleted.

**M0 note.** No code exists yet, so the test files named below are *planned* paths from the milestone plans, not existing files. The milestone that adds each guard also adds its test and flips the invariant from planned to live. An invariant without a passing test is not satisfied; it is a promise the milestone must keep.

## Permissions and path boundary (C3–C6, C9, C10)

- **INV-1:** The user's target repo is never written, at any level. The engine only writes under `--out` (default `.migration-planner/`, outside the source tree), and refuses to start if `--out` resolves inside the repo. *(planned: `test/permissions/no-repo-write.test.ts`, `scripts/repo-hash.ts` unchanged before/after a run — M1, M8)* — C3
- **INV-2:** `src/security/safeWrite.ts` is the only module that writes files; `src/security/exec.ts` is the only module that spawns a process. A lint rule (`no-restricted-imports` on `node:fs` write APIs and `node:child_process`) enforces this. *(planned: `test/permissions/single-write-point.test.ts`, `test/permissions/no-exec.test.ts`, ESLint rule — M1, M8)* — C3
- **INV-3:** No execution at L0 (the default). The `verify` field is text only. *(planned: `test/permissions/no-exec.test.ts` — M1; `test/permissions/exec-at-l0-refused.test.ts` — M8)* — C3, C5
- **INV-4:** Path boundary: every read goes through `resolveInside(root, p)`, which realpaths both sides and rejects `..`, absolute paths outside the root, and symlink escapes. *(planned: `test/permissions/path-escape.test.ts`, `test/permissions/scan-walk-refusals.test.ts` — M1)* — C4
- **INV-5:** Deny-listed files (`.env*`, keys, `.npmrc`, `.pypirc`, user denies) are never read. The AGENTS.md snippet can only *add* deny entries, never remove them. *(planned: `test/permissions/deny-list.test.ts`, `test/permissions/scan-walk-refusals.test.ts` — M1)* — C4
- **INV-6:** Autonomy is opt-in. L0 is the default; L1 needs `--level 1`; `--level 2` is refused as "not built in v0.1". A tool argument can never raise the level. *(planned: `test/permissions/level-2-refused.test.ts`, `test/permissions/level-not-raisable.test.ts` — M1, M8)* — C5
- **INV-7:** In L1, `cwd` for every spawned process is inside `<out>/<run_id>/sandbox`, the child environment is scrubbed to an allowlist, every command has a timeout, and the sandbox is a `git clone --no-hardlinks` of the repo. *(planned: `test/permissions/exec-cwd-outside-sandbox-refused.test.ts`, `test/permissions/env-scrubbed.test.ts` — M8)* — C3, C5
- **INV-8:** Commands run in L1 come only from user-owned config (CLI flags or the AGENTS.md snippet with `--trust-repo-checks`) or the pinned codemod allowlist. Never from tool arguments, packs, knowledge, prompts or the agent. *(planned: `test/permissions/exec-*.test.ts`, the `command-from-tool-arg-refused` and `unlisted-argv-refused` tests — M8)* — C9
- **INV-9:** Codemods come only from the core allowlist in `src/verify/codemods.ts`, each at a pinned version. Knowledge and packs name a codemod by ID only. *(planned: `test/permissions/unlisted-codemod-refused.test.ts` — M8)* — C9
- **INV-10:** Pack and knowledge data never execute. The knowledge and pack schemas reject unknown keys and command-like fields, and the pack lint rejects shell-like strings outside the display-text fields and any file under `knowledge/` or `packs/` that isn't JSON or Markdown. *(planned: `test/unit/knowledge.test.ts`, `test/unit/pack.test.ts`, `test/unit/lintPacks.test.ts` — M3)* — C9
- **INV-11:** The engine's only outbound network is Context7, only when configured, carrying a typed payload of library names, versions and symbol names — never repo contents. No telemetry. *(planned: `test/unit/docs/network.test.ts` — M4)* — C6
- **INV-12:** Storage is SQLite (`node:sqlite`, falling back to `better-sqlite3`) plus plain files, all through `src/store/`. No vector DB. *(planned: `test/unit/store-only.test.ts` — M1)* — C2
- **INV-13:** Runs, usages, findings and evidence carry a `repo_id` under a `campaign_id`. A request naming more than one repo is refused with "not built in v0.1". *(planned: `test/permissions/multi-repo-refused.test.ts` — M1)* — C10
- **INV-14:** stdout is the MCP protocol channel; logs and startup banners go to stderr. *(planned: `test/unit/stdout-protocol-only.test.ts` — M1)* — C1

## Gates (deterministic, no LLM)

Gates 1–6 run on the plan in `validate_plan`; gate 7 runs on each L1 stage patch. All gates re-check against real files and import no network or model code. After 3 rounds/attempts, failures go to `unresolved[]` and are never marked passed.

- **INV-15 (gate 1):** Every evidence location exists and its `snippet_hash` matches the current file, via the one shared normaliser. *(planned: `src/pipeline/gates/g1-evidence.ts`, `test/unit/gates/`, with the `bad-g1` fixture in `test/fixtures/plans/` — M6)*
- **INV-16 (gate 2):** Every usage found by `find_usages` is covered by a finding or explicitly marked out of scope with a reason. *(planned: `src/pipeline/gates/g2-coverage.ts`, `test/unit/gates/`, with the `bad-g2` fixture in `test/fixtures/plans/` — M6)*
- **INV-17 (gate 3):** Every `doc_refs` entry came from the docs tool in this run; no invented links. *(planned: `src/pipeline/gates/g3-doc-refs.ts`, `test/unit/gates/`, with the `bad-g3` fixture in `test/fixtures/plans/` — M6)*
- **INV-18 (gate 4):** Every finding with severity `high` or `blocker` has a rollback and a verify step. *(planned: `src/pipeline/gates/g4-rollback-verify.ts`, `test/unit/gates/`, with the `bad-g4` fixture in `test/fixtures/plans/` — M6)*
- **INV-19 (gate 5):** Stage order is valid: no stage depends on a change that comes later, checked against the import graph. *(planned: `src/pipeline/gates/g5-stage-order.ts`, `test/unit/gates/`, with the `bad-g5` fixture in `test/fixtures/plans/` — M6)*
- **INV-20 (gate 6):** The plan is schema-valid with no duplicate finding IDs. *(planned: `src/pipeline/gates/g6-schema-ids.ts`, `test/unit/gates/`, with the `bad-g6` fixture in `test/fixtures/plans/` — M6)*
- **INV-21 (gate 7, test integrity):** Compared with the sandbox before the stage, an L1 patch must not reduce the number of test cases or assertions, add `skip`/`only`/`todo`/`xfail` markers, delete test files or snapshots, lower coverage thresholds, or edit check definitions. A stage needing any of these goes to "Review first", never into a kept patch silently. *(planned: `src/verify/testIntegrity.ts`, `test/unit/verify/testIntegrity.test.ts`, weakened-test fixtures in `test/fixtures/g7/` all rejected — M8)*

- **INV-23:** Prompts are versioned files (`prompts/plan_migration.vN.md`); a released version is never overwritten, only a new version added. *(planned: `test/unit/promptsImmutable.test.ts` — M5)*
- **INV-24:** Pack `SKILL.md` and `references/` are generated from `packs/<pack>/pack.json` and the knowledge it uses, with a "do not edit" banner; CI fails on drift. *(planned: `test/unit/buildPack.test.ts`, the `npm run build:packs` drift check — M3)*
- **INV-25:** From M7, any change under `prompts/`, `knowledge/`, `packs/`, `src/rules/`, `src/analysis/`, `src/pipeline/{aggregate,packets,routing}.ts`, `src/pipeline/gates/` or `src/verify/` regenerates `eval/results.md` in the same change (the regression rule; replay re-runs HEAD's engine on the recorded lens submissions, so the regenerated numbers reflect the change without new runs), and the versions `results.md` records match HEAD (the engine by its package version, never a git SHA). *(planned: CI check — M7)*
- **INV-26:** The README says "currently building" until v0.1 ships (M11) with real eval numbers. *(planned: M10 review check)* — C8
- **INV-27:** Adding a pack touches only an allowlist of paths: the pack's knowledge and pack folders, one new usage adapter and its registry line, eval data, tests, docs, and the outputs its build and eval regenerate (`plugin/**`, `eval/history/`, `eval/seeded/recall.md`, its entry in `eval/seeded/ratchet.json`). Files under `eval/history/` may only be added, and another pack's ratchet entry may not change. A case's pack is the `pack` field of its `case.json`. The PR may add cases for its own pack and complete its own pack's cases that have no recorded runs on the base branch; completing a case may add files and change only `notes` and `checks` in `case.json`, and the pinned fields (`id`, `pack`, `repo_url`, `base_commit`, `merge_commit`, `pr_url`, `source`, `target`, `tags`, `license`) stay byte-identical. A pack PR is one that changes anything under `packs/` or `knowledge/`. It may never remove a pending case, its own or another pack's; that goes through D15's exception (b) in a core PR. It may record runs only for those cases, never add, complete or record runs for another pack's case, and only add lines (one per new case) to the coverage matrix in `eval/cases/README.md`. Existing cases and runs are add-only on every PR (INV-45). A new ratchet entry must equal the measured recall. Everything else, including `scripts/` and the eval scoring code, is protected. *(planned: `scripts/check-core-untouched.ts` — M10; the ratchet check — M2)*

## Out of scope (see `design.md` D16)

- **INV-42:** Every `out_of_scope` entry has a non-empty reason and a `written_by` (`scope`, `engine` or a lens). A lens can only mark usage IDs from its own packet, a usage keeps one entry (`scope`, then `engine`, then a lens), and every usage that matches no composed rule and that no finding covers gets the engine's `no rule in range` reason, in every run size. A usage covered by a finding never also gets the engine's reason or a lens entry; a lens mark on it is recorded as a conflict event. Scope-excluded usages are in no lens packet, and one that a finding still covers keeps its `scope` entry: the usage is removed from the finding's coverage and recorded as a conflict event, and the finding stays in the plan for its other usages. A finding left covering no usage is kept out of the plan and listed in the run report. A submission in which one lens both marks a usage out of scope and writes a finding on it is rejected whole, with no item stored, and counts toward the lens retry policy. *(planned: `test/unit/submitFindings.test.ts`, `test/unit/packets.test.ts` — M5; `test/unit/aggregate.test.ts` — M6)*

## Pack merge gate (see `design.md` D17)

- **INV-43:** On every PR, CI replays the recorded runs (engine runs through HEAD's engine, baseline runs re-scored from their recorded Markdown). Recall is golden-set usage recall pooled over a pack's cases; the engine's figure is its worst-case pooled recall (each case's lowest-recall run) and the baseline's is its best-case pooled recall (each case's highest-recall run), so renumbering runs never changes either. For each pack under `packs/` at HEAD, the PR fails if: the pack has no band in `eval/results.md` on the base branch and the engine's figure is not above the baseline's (`nextjs-upgrade`, which sets the first band in M7, is exempt); the PR adds golden cases to a pack other than `nextjs-upgrade` and, over all its cases, the engine's figure is not above the baseline's (for `nextjs-upgrade` this is shown, not enforced); the engine's figure over the cases in the base band that are present at HEAD falls below the low end of the base band over the same cases (skipped, and said so in the CI job output, when the base branch has no band for the pack); the pack has fewer than 2 golden cases or no true changed usage; any case has fewer than 3 runs on either side, or run counts differ across the pack's cases or between the engine and the baseline; the pack's runs, on both sides, don't all share one host product and model; or a pinned case commit can't be fetched and isn't cached (a named `case_commit_unavailable` error, never a skipped case). It also fails if the committed `eval/results.md` differs from the re-scored one. `results.md` is a pure function of HEAD's tree: it holds no generation time, takes cost and wall time from the recorded runs, records the engine by its package version, always reports each pack's all-case beat result, and renders `eval/cases/REMOVED.json`; verdicts that depend on the base branch (regression pass or fail, a skipped regression check, a reported widening beat result) go only in the CI job output. *(planned: CI pack gate, `test/unit/eval/` pack-gate test — M7; applied to the Django pack — M10)*
- **INV-44:** The pack gate and `eval/results.md` score only engine runs under the current prompt version that `prompts/manifest.json` names at HEAD, and only baseline runs whose recorded hash of `eval/baseline/prompt.md` equals HEAD's; a pack with a baseline run of another hash fails. Cases whose pack doesn't exist under `packs/` at HEAD are listed as pending in `results.md`, never scored or failed. Every engine run records its ingest arguments, `set_scope` answers, every `run_docs` entry whatever its `fetched_by` (URL, content, `doc_id`, `fetched_by`, `official`, status), each `validate_plan` round's lens submissions in order, and the file, span and `snippet_hash` of every usage ID its packets carried; `truth.json` stores the same three per true usage. Replay never calls a model or Context7 and adds no agent turns: it applies the recorded arguments and scope answers, re-registers every recorded doc with no network, and feeds the rounds in order, stopping at the first round HEAD's gates pass, through HEAD's `find_usages`, packets, `merge_findings` and gates, keeping each run's recorded size and lens set (a run HEAD would size differently is flagged in the report, never re-sized). Later recorded rounds are not fed. A recorded input HEAD rejects is handled as the live flow would and the run is flagged: a scope answer HEAD no longer offers takes the default, a submission HEAD's `submit_findings` rejects counts as that lens's invalid output (using the recorded retry attempts, then `lens.gap`), and a doc HEAD's version pin refuses is not registered. A failure HEAD's gates newly raise, with no recorded round left, goes to `unresolved` and is scored, never patched. Recorded usage IDs and truth usages are matched to HEAD's usages by file, span and `snippet_hash`, never by usage ID, so renumbering IDs leaves the score unchanged; a recorded finding with no matching HEAD usage is dropped, counted as a miss and listed, and `truth.json` is never re-derived for an existing case. A change to usage spans or the snippet normaliser therefore fails the regression check on the affected cases unless, in the same core PR, they are removed under exception (b) and re-added under new IDs with fresh truth and new runs; the re-added cases are new cases of their pack, outside the regression check's base cases and inside the all-case beat check. *(planned: `test/unit/eval/` pack-gate and replay tests — M7)*

## Eval data (see `design.md` D15)

- **INV-45:** On every PR, existing cases (case folders with recorded runs on the base branch) and recorded runs are add-only: no file in an existing case's folder is added, changed or deleted, the folder is not deleted, no existing run is changed or deleted, and no run is added to a set that already has runs on the base branch. A set is a case's engine runs under one prompt version, its L1 set under that version (`eval/runs/<case>/<prompt_version>/l1/<n>/`, which never counts toward N or recall) or its baseline runs; runs under a new prompt version, and a case's first L1 set under a version, are plain adding. The one allowance is `annotations.json`, which may gain appended entries (or be added with its first entries) while its existing entries stay frozen. Deleting a single run without removing its case always fails. A pending case (no recorded runs) is removed only through (b), never by a pack PR. The only exceptions are (a) a core PR that changes `eval/baseline/prompt.md`, which may replace baseline runs and nothing else (no engine run, no case file), and (b) removing a case with all its runs in a core PR (one that changes nothing under `packs/` or `knowledge/`) that adds an entry to the add-only `eval/cases/REMOVED.json`; an entry with no matching case removal fails, and existing entries are never edited or deleted. Exception (b) is also how a change to usage spans or the snippet normaliser re-adds its affected cases under new IDs. Its maintainer review is enforced by GitHub's required code-owner review through `.github/CODEOWNERS`, not by CI (`design.md` D15). *(planned: `scripts/check-eval-add-only.ts`, `test/unit/eval/` add-only test — M7)*
