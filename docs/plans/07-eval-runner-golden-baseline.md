# M7 - Eval runner, 5 golden cases, baseline run

**PRD refs:** section 10 (tiers, metrics, regression rule), section 12 (eval smoke in gates), section 15 (honest claims). **Done when:** `eval/results.md` is published, misses included.

## Scope

- In scope:
  - a local eval runner that is free to run
  - 5 golden cases (real public Next.js major-upgrade PRs, including at least 1 messy or failed one)
  - the seeded-defect tier from M2
  - a baseline run of the same host agent without the engine
  - all PRD section 10 metrics, including the repo-untouched hash and cost and time
  - the regression rule wired into CI
  - the pack gate (`docs/design.md` D17) and the eval add-only check `scripts/check-eval-add-only.ts` (D15), on every PR
  - `.github/CODEOWNERS` and branch protection with required code-owner review
- Out of scope: outcome metrics for L1 (first-pass verify rate, retries, gate 7 incidents). M8 adds them to this runner, so the case format and metrics module are built to take extra metric groups without a rewrite.

## Tasks

1. **Case format (`eval/cases/<id>/case.json`).**
   - Fields: `id`, `pack`, `repo_url`, `base_commit` (the parent of the migration), `merge_commit`, `pr_url`, `source` and `target` (each `{framework, version}`, as the M0 records use), `license`, `checks` (the check commands the case's repo uses, for M8; optional here, but required before its runs merge on any case M8 will use for L1, since `checks` freezes once a case has runs), `notes` and `tags` (for example `messy` or `monorepo`).
   - Ground truth is derived deterministically. `scripts/derive-truth.ts` diffs base against merge and maps the changed hunks to M2 usages at base, writing `truth.json` (true changed usages, each with its file, span and `snippet_hash`, touched files, and per-file edit size, which is used for severity calibration). `truth.json` is never re-derived for an existing case (one with recorded runs, `docs/design.md` D15); replay matches its usages to HEAD's by file, span and `snippet_hash` (task 3).
   - The diff and checkout are done by **eval tooling**, outside the engine, in a temp clone under the eval workspace. The engine only ever sees a read-only path (C3 still holds for the engine).
2. **Pick and pin 5 cases.** Extend the M0 Next.js list to 5, with at least one messy case: a partial upgrade, a reverted PR, or a PR with follow-up fixes. Prefer cases whose repo has a runnable test suite, so M8 can reuse them. Record why each was chosen.
   - **Every committed case needs an open licence** from the finder's allowlist. The M0 messy case `nextjs-chiarel-6-messy` has none, so M7 replaces it with a licensed messy Next.js upgrade (a revert, a partial upgrade or one with follow-up fixes) and removes it from `eval/cases/`. If no licensed messy case can be found, stop and raise it with the maintainer rather than keeping an unlicensed one (see `eval/cases/README.md`, open items).
   - **Pick for spread, not count.** `eval/cases/README.md` keeps a coverage matrix: router (app, pages or both), monorepo or single package, one major hop or several, test runner, data layer, and size of the real diff. A new case should fill an empty cell rather than repeat a covered one, and empty cells are listed as known gaps in `results.md` (`docs/design.md` D7). The Django cases from M0 are added in M10.
3. **Runner (`eval/runner.ts`).**
   - Modes:
     - `--tier unit|seeded|golden|baseline|all`
     - `--smoke`: the seeded tier plus 1 golden case, used in milestone gates
     - `--case <id>` and `--pack <name>`
   - For each case: clone or fetch into `eval/.work/<id>` (gitignored), check out the base commit, record `repo_hash_before`, drive the planner, then record `repo_hash_after`. A mismatch fails the case outright.
   - **Driving the host agent at zero cost.** The recorded runs (`eval/runs/<case>/<prompt_version>/<n>/` for the engine, `eval/runs/<case>/baseline/<n>/` for the baseline, and from M8 `eval/runs/<case>/<prompt_version>/l1/<n>/` for L1 runs, a set of its own that never counts toward N or the pack gate's recall and that M8's replay re-scores from its `stage_attempts`) are produced by running the flow in Claude Code or Cursor under the user's existing subscription. Every engine run, whatever its size, records the ingest arguments, the `set_scope` answers, every `run_docs` entry whatever its `fetched_by` (`agent`, `engine` or `knowledge`), with URL, content, `doc_id`, `fetched_by`, `official` and status, each `validate_plan` round's lens submissions in order, including any retry attempts within a round (with the file, span and `snippet_hash` of every usage ID its packets carried), the transcript, the cost and wall time, and the host product and model. The default is a *replay* mode (`docs/design.md` D17):
     - For an engine run, it applies the recorded ingest arguments and scope answers, re-registers every recorded doc itself with no network (no Context7), and feeds the recorded rounds' lens submissions in order through HEAD's deterministic engine: `find_usages`, the packets (to match usage IDs and snippet hashes), `merge_findings` and the gates, on the case's base commit. It stops at the first round HEAD's gates pass, as the live flow does, and scores that plan; later recorded rounds are not fed. It adds no agent turns: a failure HEAD's gates newly raise, with no recorded round left, goes to `unresolved` and is scored, never patched. It scores the result and never calls a model or a paid service, so knowledge and engine changes show up without new runs.
     - Replay keeps each recorded run's size and lens set and does not re-run sizing. If HEAD would size the case differently, the report flags the run, and new live runs measure the change.
     - Recorded usage IDs, and the usages in `truth.json`, are matched to HEAD's usages by file, span and `snippet_hash`, never by usage ID, so an adapter change that renumbers IDs changes nothing. A recorded finding with no matching HEAD usage (the code is no longer found, or its `snippet_hash` changed) is dropped and counts as a miss, and the report lists those.
     - A baseline run is re-scored from its recorded Markdown, since there is no engine to re-run.
     - When HEAD rejects a recorded input before the gates, replay handles it as the live flow would and flags the run: a recorded scope answer HEAD no longer offers takes the default; a recorded submission HEAD's `submit_findings` rejects counts as that lens's invalid output under the retry policy, using the recorded retry attempts if there are any, and then `lens.gap`; a recorded doc HEAD's version pin refuses is not registered.
     - **Case commits.** This eval tooling fetches each case's pinned commits, outside the engine, and CI caches them. A pinned commit that can't be fetched and isn't cached fails the run closed with the named error `case_commit_unavailable`; the case is never skipped. The remedy is `npm run cases:verify` (task 8) and replacing the case through the case-removal path (`docs/design.md` D15, exception b).
     - A *live* mode uses the optional CLI with the user's own API key (PRD section 1). It is opt-in and reports token cost. The runner never needs a paid service by default (C1). **Decision to record:** how live runs are triggered for each host. Claude Code headless (`claude -p`) is the likely candidate; check the current docs at M7 start.
4. **Baseline (`eval/baseline/`).** The same host agent and the same task prompt text, but with **no** engine configured (no MCP server, no skill). Ask for a plan in Markdown and parse it into best-effort findings (file:line mentions, severities) using `eval/baseline/parse.ts`. Score it with the same metrics. Citations that don't resolve count as invalid, not as skipped. Each recorded baseline run stores its Markdown plan, the hash of `eval/baseline/prompt.md` it was made with, and the host product and model. Changing `eval/baseline/prompt.md` is a core PR that must replace every pack's baseline runs (`docs/design.md` D15, exception a); a baseline run with another hash fails the pack gate.
5. **Metrics (`eval/metrics.ts`).**
   - usage recall (true changed usages covered)
   - file precision (listed files that the real PR also touched)
   - evidence validity (share of resolving citations, with a target of 100%)
   - severity calibration (the share of high and blocker findings whose files needed non-trivial edits, with the threshold defined in code)
   - the false-alarm rate for high and blocker findings
   - seeded precision: a finding that proposes a change on a `no_change` or `no_finding` seeded entry (M2) counts as a false alarm; marking a `no_change` entry out of scope is correct
   - the `out_of_scope` rate, split by `written_by` (`scope`, `engine`, lens), so engine-written `no rule in range` entries don't hide what the lenses marked
   - unresolved count
   - cost (tokens if reported) and wall time, both taken from the recorded run, never measured while re-scoring it
   - repo-untouched (bool)
6. **Results (`eval/results.md`, generated).** One table per tier and per pack: case × metric, plus a **with engine vs. without** comparison table. It includes a "Misses" section listing every false negative and false alarm with a link, and records the versions of the pack, prompt, gates (a code hash) and engine. The engine is recorded by its package version, never a git SHA, since a commit can't contain its own SHA. History is kept in `eval/history/<date>-<base-sha>.json`, where `<base-sha>` is the SHA of the PR's parent (base) commit, for the same reason. `results.md` is a pure function of HEAD's tree (`docs/design.md` D17): it holds no generation time, and its cost and wall time come from the recorded runs, so the same tree always gives the same bytes. It always reports each pack's beat result over all its cases, which needs only HEAD, and renders `eval/cases/REMOVED.json`, the committed, add-only list of removed cases (`id`, `reason`, `pr`; D15). Verdicts that depend on the base branch (regression pass or fail, a skipped regression check, the enforced or reported widening beat result) go in the CI job output, never in `results.md`.
   - **Which runs count (`docs/design.md` D17).** `results.md` and the pack gate use only engine runs under the current prompt version that `prompts/manifest.json` names at HEAD, and only baseline runs whose recorded prompt hash equals HEAD's hash of `eval/baseline/prompt.md`; a pack with a baseline run of another hash fails the gate. A new prompt version therefore needs N new engine runs for every case of every pack before the gate can score it; adding them is a core PR (one that changes nothing under `packs/` or `knowledge/`, `docs/design.md` D15). Cases whose pack doesn't exist under `packs/` at HEAD (such as the Django cases from M0) are listed as pending, not scored or failed.
   - **Noise band (`docs/design.md` D17).** Every golden case of a pack has the same number N of these engine runs and the same N of baseline runs, with N at least 3, all made with the same host agent: the same host product and model on both sides, as each run records (the host's CLI version may differ). Golden-set usage recall is pooled over the pack's cases (true changed usages covered, over all true changed usages). The engine's figure is its worst-case pooled recall: each case's lowest-recall engine run, pooled. The baseline's figure is its best-case pooled recall: each case's highest-recall baseline run, pooled. `results.md` records, per pack and per side, the band from the pooled recall of each case's worst run to the pooled recall of each case's best run, and each case's covered and true changed usages for its worst and best run, so the band can be recomputed over any set of the pack's cases.
   - **PR-missed annotations.** A real PR can itself miss a required change, which makes a correct finding score as a false alarm. A reviewer may record this in `eval/cases/<id>/annotations.json` (finding, reason, reviewer, date). The file is hand-reviewed and never generated. On an existing case it may only gain appended entries (or be added with its first entries); existing entries are frozen (`docs/design.md` D15); M9's `record_feedback` export may only propose entries. Annotated findings are listed in a separate "PR missed" section. **Headline metrics are always computed from raw truth.** An annotation only adds an adjusted figure next to them, never replaces them, and `truth.json` is still never hand-edited.
7. **Regression rule in CI.** From this milestone on, a path filter on `prompts/`, `knowledge/`, `packs/` (including the generated `SKILL.md`), `src/rules/`, `src/analysis/` (usage adapters, risk and sizing, which decide what is found and whether the lenses run), `src/pipeline/{aggregate,packets,routing}.ts`, `src/pipeline/gates/` and `src/verify/` (codemod registry and gate 7, from M8) requires `eval/results.md` to be regenerated in the same PR (CI checks that the versions the results record, the hashes and the engine's package version, match HEAD). Because replay re-runs HEAD's engine on the recorded lens submissions (task 3), the regenerated numbers reflect the change without new runs. The smoke tier runs on every PR in replay mode, for free: replay calls no model and no paid service (C1). The pinned case commits are fetched by eval tooling, outside the engine, and CI caches them; C6 covers only the engine's own network, so it is unaffected.
   - **Pack gate (`docs/design.md` D17).** On every PR, not only those the path filter catches, CI replays the recorded runs (task 3). It checks every pack that exists under `packs/` at HEAD, and only those.
     - **Beat check.** It fails the PR if a pack at HEAD has no band in `eval/results.md` on the base branch and its engine worst-case pooled recall is not above the baseline's best-case pooled recall. This applies whichever PR adds the pack's cases, not only the PR that creates `packs/<pack>/`. `nextjs-upgrade` sets the first band in this milestone and is exempt; the beat check applies from the Django pack (M10), and `results.md` states plainly where the engine does not beat the baseline (acceptance criteria). A PR that adds golden cases to a pack that was beat-checked when added (every pack but `nextjs-upgrade`) also fails unless, over all the pack's cases including the new ones, the engine's worst-case pooled recall is above the baseline's best-case pooled recall. For `nextjs-upgrade`, that result is shown (`results.md` always shows each pack's all-case beat result) but not enforced.
     - **Regression check.** It fails the PR if a pack's engine worst-case pooled recall, over the cases in the base branch's band that are also present at HEAD, falls below the low end of the base band recomputed over the same cases. The PR's own regenerated band is never the reference. When the base branch has no band for a pack, the check is skipped for that pack and the CI job output says so. When a PR widens a pack with new golden cases, those cases are not in the base band and so are left out of this check (the beat check above still counts them). They must have the same N as the pack's existing cases, and their runs join the band in the PR's regenerated `results.md`, which becomes the base for later PRs.
     - **Counts.** It fails the PR if a pack at HEAD has fewer than 2 golden cases or no true changed usage across them, if any case has fewer than 3 runs on either side, if the run counts differ across a pack's cases or between the engine and the baseline, if a baseline run's prompt hash differs from HEAD's, or if a pack's runs, engine or baseline, don't all share one host product and model. It fails closed with `case_commit_unavailable` when a pinned case commit can't be fetched and isn't cached (task 3).
     - It also fails a PR whose committed `eval/results.md` differs from the re-scored one.
   - **Eval add-only check (`scripts/check-eval-add-only.ts`, `docs/design.md` D15).** It runs on every PR from this milestone, when recorded runs first exist, not only on pack PRs. A case's pack is the `pack` field of its `case.json`; a *core PR* changes nothing under `packs/` or `knowledge/`, and a *pack PR* changes something there (D15).
     - It fails when a file in an existing case's folder (a case with recorded runs on the base branch) is added, changed or deleted, when that folder is deleted, when an existing recorded run is changed or deleted, or when a run is added to a set that already has runs on the base branch. A set is a case's engine runs under one prompt version, its L1 set under that version (task 3) or its baseline runs. Runs under a new prompt version, and a case's first L1 set under a version, are plain adding. Deleting a single run without removing its case always fails.
     - The one allowance: an existing case's `annotations.json` may gain appended entries (or be added with its first entries). Existing entries are frozen.
     - A pending case (no recorded runs) may be removed only through exception (b), never by a pack PR.
     - The only exceptions are D15's: (a) a core PR that changes `eval/baseline/prompt.md` may replace baseline runs, every pack's, and nothing else (no engine run, no case file); (b) a case may be removed together with all its runs in a core PR reviewed by a maintainer, and the PR must add its entry to `eval/cases/REMOVED.json`. An entry with no matching case removal fails, and existing entries may not be edited or deleted. Exception (b) is also how a change to usage spans or the snippet normaliser re-adds its affected cases under new IDs, with fresh truth and new runs, in the same core PR; the re-added cases are new cases of their pack, outside the regression check's base cases and inside the all-case beat check (D17).
     - The review is enforced by GitHub's required code-owner review: `.github/CODEOWNERS` names a maintainer for `eval/cases/**` and `eval/runs/**`, and CI does not try to check reviews. M10's `check-core-untouched` adds the pack-PR rules on top.
   - **Branch protection.** Enable branch protection on `main` with "Require review from Code Owners", and record that it is on in `docs/design.md`. GitHub doesn't let an author approve their own PR, so while there is a single maintainer, a removal or baseline-prompt PR the maintainer opens needs a second code owner. Until there is one, this is a known limit, recorded in `docs/design.md` with the setting.
8. **Golden-case tools (`docs/design.md` D11).** Maintainer tooling under `scripts/`, outside the engine. Both use the `gh` CLI and git over the network, never run in default CI, and are never imported by `src/`.
   - **Finder (`scripts/find-golden-cases.ts`, `npm run cases:find -- <pack> --from <v> --to <v>`).** Searches GitHub for merged PRs whose title names the upgrade, excluding bots, pacing one search about every 7 seconds (GitHub's secondary rate limit). For each hit it checks:
     - the licence, against an allowlist of open licences
     - that the base commit is the merge commit's first or only parent, and both can be fetched
     - the from and to versions, read from the lockfile at base and merge, never from the PR title
     - whether a test script or CI workflow exists at base
     - the size of the diff, and how much of it is lockfile churn

     It writes candidate `case.json` files with `status: candidate` and a vetting report to `eval/.work/candidates/` (gitignored). Each candidate is marked with the coverage-matrix cell (task 2) it would fill. A human vets candidates with the `add-golden-case` skill and moves the accepted ones into `eval/cases/`. Nothing is added automatically.
   - **Re-checker (`scripts/verify-case.ts`, `npm run cases:verify -- <id>|--all`).** Re-checks committed cases against GitHub: the commits are still fetchable, the parentage holds, the versions at base and merge match the record, the licence is unchanged and on the open-licence allowlist, and the declared test command exists at base. It prints one line per check and exits non-zero on any mismatch. Run it before a live eval and whenever a case looks wrong.
9. **Threshold tuning input.** Export the per-finding confidence vs. correctness pairs to `eval/calibration.csv`. M9 uses them to tune the 0.6 threshold.

`eval/runner.ts`, `eval/metrics.ts`, `eval/baseline/{prompt.md,parse.ts}`, `eval/cases/<5 ids>/{case.json,truth.json,annotations.json?}`, `eval/cases/README.md` (coverage matrix), `scripts/{find-golden-cases,verify-case,check-eval-add-only}.ts`, `test/fixtures/github/` (recorded API responses), `scripts/derive-truth.ts`, `eval/results.md`, `eval/history/`, `eval/runs/` (recorded engine and baseline runs), `eval/calibration.csv`, `.github/workflows/ci.yml` (or a local `npm run ci` if CI is not used), `.github/CODEOWNERS` (a maintainer for `eval/cases/**` and `eval/runs/**`), `eval/cases/REMOVED.json` (empty list at first), `test/unit/eval/*.test.ts`.

## Tests

- **Metrics:** unit tests with hand-computed fixtures for recall, precision, calibration and false-alarm rate.
- **Seeded precision:** a finding proposing a change on a `no_change` or `no_finding` entry counts as a false alarm, and an `out_of_scope` mark on a `no_change` entry does not.
- **Golden-case tools (offline, on recorded GitHub responses):** the finder rejects a bot PR, an unlicensed repo, a PR whose lockfile doesn't show the version change, and a base that isn't the merge commit's parent, and it never writes into `eval/cases/`. The re-checker fails on a planted parentage mismatch, a planted version mismatch, a missing test command and a repo with no licence.
- **Annotations cannot move the headline:** adding an `annotations.json` entry leaves every headline metric byte-identical and changes only the adjusted column and the "PR missed" section.
- **Truth derivation:** a tiny synthetic repo with two commits gives the expected `truth.json`.
- **Repo-untouched:** the runner fails a case when the target hash changes. Tested by planting a write in a fake planner, which must be caught.
- **Replay determinism:** re-scoring the same recorded run twice gives byte-identical metrics. Generating `results.md` twice, with a faked clock set to different times and fixture runs whose recorded wall times differ from each other, gives identical bytes both times. Regenerating `results.md` on the commit after a case removal gives identical bytes to the one committed with the removal.
- **Replay inputs:** a `full` fixture run with a non-default scope answer, and a fixture whose findings cite a doc registered in the run, both pass gate 2 and gate 3 under replay, with no Context7 call, no network and no new agent turn; a fixture citing an engine-fetched doc and a `fetched_by: knowledge` fallback doc passes gate 3 the same way. A recording with two rounds whose first round HEAD's gates pass is scored on round 1, and round 2 is not fed. A fixture whose HEAD gates raise a failure the recording never saw, with no round left, puts it in `unresolved` and scores it. A fixture where HEAD no longer offers a recorded scope answer, rejects a recorded submission (with one recorded retry attempt, then `lens.gap`) and refuses a recorded doc by its version pin replays with the default answer, the retry policy and the doc unregistered, and the run is flagged.
- **Truth matching:** an adapter change that renumbers usage IDs leaves the replayed score unchanged, and `truth.json` for an existing case is never rewritten. A snippet-normaliser change fixture fails the regression check on its affected cases, and passes only when the same core PR removes them under exception (b) and re-adds them under new IDs with fresh truth and new runs, after which they are beat-checked over all cases as new cases.
- **Case commits:** with a pinned commit neither fetchable nor cached, the gate fails with `case_commit_unavailable` rather than skipping the case.
- **Eval add-only (`scripts/check-eval-add-only.ts`):** an eval-only PR that edits an existing recorded run fails; so do a file added to, changed in or deleted from an existing case's folder and a run added to an existing set. A PR that changes `eval/baseline/prompt.md` and replaces the baseline runs passes, and runs added under a new prompt version pass. A case removal that leaves some of its runs behind fails, and so do a removal in a PR that also changes `knowledge/` or `packs/`, a removal with no `eval/cases/REMOVED.json` entry, and an edit to an existing entry. A baseline-prompt change also fails in a PR that changes `knowledge/` or `packs/`, or that also edits or replaces an engine run or a case file. Deleting a single existing run with no case removal fails. A first L1 set added to an existing case passes, and a later run added to that L1 set fails. Appending an entry to an existing case's `annotations.json` passes, and editing or deleting an existing entry fails. A core PR deleting a pending case without a `REMOVED.json` entry fails. A `REMOVED.json` entry added with no matching case removal fails, and so does deleting an existing entry.
- **Replay re-runs the engine:** changing a fixture rule's knowledge changes the replayed score without new runs. A recorded finding whose usage HEAD no longer finds at the recorded file, span and `snippet_hash` is dropped, counted as a miss and listed in the report. A baseline run's score comes from its recorded Markdown alone, and no replay calls a model. Replay keeps a recorded run's size and lens set: a fixture whose knowledge change makes HEAD size the case differently is replayed at its recorded size and flagged in the report.
- **Pack gate (`test/unit/eval/`):** on fixture runs:
  - a new pack whose engine worst-case pooled recall equals the baseline's best-case pooled recall fails, and one just above it passes
  - a pack whose worst-case pooled recall falls below its base-branch band fails, including when the PR re-records lower runs and regenerates `results.md` to match them
  - renumbering a pack's runs (swapping which run of a case is run 1 and which is run 2) leaves both figures and the result unchanged
  - pooled recall is checked against a hand-computed fixture with cases of different sizes
  - a widening PR whose new hard case lowers the all-case recall does not fail the regression check, while a drop on the base cases does
  - a widening PR whose new cases drop a beat-checked pack to or below the baseline over all its cases fails; the same widening of `nextjs-upgrade` passes, with the all-case beat result shown in `results.md` and the verdict only in the CI job output
  - 2 runs per case fails; one case with 4 runs while the others have 3 fails; engine and baseline run counts that differ fail
  - a pack at HEAD with zero golden cases fails, and so does one with a single case or with no true changed usage
  - a pack added in one PR with no cases, and its cases added in a later PR, is still beat-checked in the later PR and fails it when the engine doesn't beat the baseline
  - `nextjs-upgrade` with no base band is not beat-checked, and the regression check is skipped for it with a line in the CI job output saying so, while `results.md` holds no base-branch verdict
  - a case whose pack is not under `packs/` (an M0-style Django case with only `case.json`) is listed as pending and doesn't fail the gate
  - an engine run under an older prompt version is not scored, and a baseline run whose prompt hash differs from HEAD's fails
  - one engine or baseline run with a different host model than the pack's other runs fails, so does one with a different host product and the same model, while a different host CLI version passes
  - removing a case from HEAD pools the regression check over the remaining cases on both sides
  - a hand-edited `results.md` fails, also in a PR that touches nothing outside `eval/`
- **Baseline parser:** extracts file:line and severity from sample Markdown, and unresolvable citations are counted as invalid.
- **Permissions:** the full suite, still in the gate.

## Acceptance criteria

- `npm run eval -- --tier all` (replay mode) produces `eval/results.md` with 5 golden cases, the seeded tier and the baseline comparison, all metrics populated, and misses listed.
- Every case reports `repo_untouched: true`.
- Evidence validity for the engine is 100%, because the gates enforce it. If it isn't, that is a bug filed before M7 closes.
- `results.md` states plainly where the engine does **not** beat the baseline.
- `results.md` records the noise band for the Next.js pack and the baseline, from the same number of recorded runs per case on both sides, at least 3, and the CI pack gate runs on it.
- `results.md` lists the empty cells of the case coverage matrix as known gaps, and the Django cases from M0 as pending.
- `npm run cases:verify -- --all` passes on every committed case. Every case has an open licence, at least one Next.js case is tagged `messy`, and `nextjs-chiarel-6-messy` is no longer in `eval/cases/`.

## Risks

- **Finding 5 good migrations takes time (PRD section 15).** Mitigation: the search started in M0. A messy case is acceptable, and it is also required.
- **Ground truth is noisy.** Real PRs include unrelated refactors. Mitigation: `truth.json` excludes files with no source-library usage at base, and `notes` record any manual exclusions with a reason.
- **Variance in the host agent between runs.** Mitigation: record the transcripts, keep at least 3 runs per case and report their spread as the noise band (D17). Replay keeps CI deterministic.
- **Cost.** Mitigation: replay is the default, and live runs are opt-in on the user's own key with costs reported.

## Must not break

Gates, permissions, pack lint and prompt immutability.
